Constraints for this sprint
There is no paid Apple Developer membership. Everything here is buildable and testable without one. A free Apple Account in Xcode can install the app on your own iPhones with short-lived provisioning. What a free account cannot do, and is therefore out of scope:
Push notification delivery on a device
Real App Store purchases (Xcode StoreKit configuration testing still works)
TestFlight or App Store submission
Universal links. Use the existing verdure:// URL scheme for invite and deep-link testing.
Nothing is deployed. No billing change, production deploy, environment flip or key rotation.
Do not modify ranking. Weights, signals and the interest synonym map in ranking.ts are being tuned against a golden set this sprint. Changing them independently would invalidate that measurement.

A. Location-based partners
Partner offers leave the organic events feed and appear in their own location-based surfaces. Commercial content inside a discovery feed, however well labelled, erodes trust in every recommendation around it.
A1 — Remove partners from the organic feed
functions/src/partners.ts lines 38 and 47–48 still include "events_feed" in SurfaceId and ALLOWED_SURFACES. Remove it. Keep planner, rewards and event_detail; add map and near_you.
Add a test that fails if any partner content appears in For You or Everything.
A2 — Partner map layer
Partners appear on the map as their own pin type — a distinct glyph, in a colour other than the event accent.
Toggleable, on by default, persisted per user
Tapping a pin shows the partner, perk, point cost and walking distance
Existing dismissal and trust rules apply
A3 — "Near you" card
When the app opens and a partner with a live perk is within walking distance, show one card at the top of Discover:
Joe's Café · 2 min away · 15% off
Uses the existing When-In-Use location. No new permission.
One card maximum; dismissible; dismissal remembered via dismissPerk
Silence when nothing is within walking distance — never fall back to something further
Time-appropriate: food at meal times, coffee in the morning, activities at weekends
A4 — Rewards sorted by distance
Add a Nearby sort to perks in Rewards: closest first, the default when location is available, existing order otherwise.
A5 — RSVP-triggered partner notification
When a user RSVPs to an event and a partner with a live perk is within a short walk of the venue, send one notification before the event:
Going to the farmers market Saturday? Joe's Café is 2 minutes away — 15% off with your code.
No background location — the user has already said where and when they will be
Through the existing notifier; counts toward MAX_PUSH_PER_WEEK, never in addition
One per RSVP; respects quiet hours; its own preference toggle
Server logic tested in the emulator. Device delivery needs the paid membership — record it as untested, not passed.
A6 — Opt-in live location alerts (build last in A; cuttable)
A notification as someone walks near a partner. Off by default.
A dedicated toggle — "Tell me about deals near me" — with plain consent language stating what will be sent and why location is needed. App Store Review Guideline 4.5.4 requires explicit opt-in for promotional notifications, plus an in-app opt-out.
Request Always location only from inside this toggle's flow, never at launch and never as a condition of anything else
Excluded entirely for minor accounts
iOS caps region monitoring at 20 regions: monitor the nearest 20 eligible partners and swap using significant-location-change, never continuous GPS
Counts toward the shared weekly push cap
If it ships, update the App Privacy answers and privacy policy in the same change
Done when: events_feed is removed and a test proves no partner content reaches organic results; partner pins are a distinct toggleable layer; the Near you card appears only within walking distance with no new permission; Rewards has a Nearby sort; the RSVP notification fires once per RSVP within the weekly cap; A6, if built, is off by default, consent-gated, excluded for minors and capped at 20 regions.

B. Staff console
Several built features cannot be used with real data, because the actions they depend on have no interface:
Real partner perks cannot be loaded. seed-partners.mjs is placeholder-only and correctly refuses to run outside the emulator. There is no other path.
Reports cannot be reviewed. moderateContent exists, but no one can see the queue.
Organizers cannot be approved. approveOrganizer and listOrganizerApplications exist with no interface.
Build an authenticated console under /admin on the existing website. Its users are not engineers, so a command-line tool is not a substitute.
B0 — Access and accountability
Access via a Firebase Auth admin custom claim, granted only through a CLI script. No self-service path to admin.
Every authorization check is server-side, using the existing isAdmin() in common.ts. The interface hides controls for convenience only; it is never the gate.
Every admin action writes an audit record: actor, action, target, time, before and after. Admin-readable only and immutable.
A red-team case for every admin path proving a non-admin is refused.
B1 — Moderation queue
Pending reports from moderationQueue, oldest first, with hours since first report shown prominently and highlighted past 20 hours
The reported content in context, reasons and report count
Actions through moderateContent — remove, restore, warn, suspend — each requiring a reason
Filters by status and content type; history of resolved items
B2 — Organizer approvals
Pending applications through listOrganizerApplications
Approve or reject through approveOrganizer, with a reason
The 50-approval cap displayed: used and remaining
B3 — Partners and perks
Create a partner: business name, category, address — geocoded on save and stored with coordinates for Section A — and contact details
Agreement on file is required to activate. A partner cannot go live without a recorded confirmation: who agreed, when, and a reference to the written confirmation. This is the production equivalent of seed-partners.mjs refusing to run — it makes it impossible to put a business's name on an offer it never agreed to.
Create a perk: title, terms, point cost (500–2,000, enforced server-side), optional earlyAccessUntil, expiry date
Load codes by CSV: validate format, reject duplicates against existing codes, report how many loaded
Low-stock warning below 10 unused codes
Deactivate a partner or perk immediately, with a reason
B4 — Submissions inbox
Read and resolve entries from the website forms built in Section E: support requests, organizer interest and merchant interest. Mark each handled, with a note.
B5 — Operations overview
Ingestion health per source: last successful run, events returned, last error. A source that throws must appear here, not only in logs.
Active events by source and the current duplicate rate
Pending reports with the oldest report's age; pending organizer applications
Month-to-date reward spend against the $200 treasury cap; planner and SerpApi spend
Done when: admin access is grantable only through the CLI and enforced server-side; every action is audited; a report can be resolved end to end; an organizer can be approved with the cap shown; a partner with a recorded agreement can be created, given a perk and loaded with CSV codes, and appears on the map from Section A; a partner without one cannot be activated; the overview surfaces ingestion failures. Every admin path has a red-team case.

C. Park guide, trail overview and offline packs
Parks are central to Verdure's identity and to its largest segment. Parents want to know before they drive whether a park has a playground for their child's age, restrooms and water — and what is happening there this weekend. Official, openly licensed data answers all of it.
Park and trail information is free online — safety and discovery are never paywalled. Downloading it for offline use is Verdure+.
C1 — Data sources
A separate place-data pipeline, distinct from event ingestion, refreshed weekly, following the same rules: published data only, terms checked first, and fail loudly with failures shown in the staff console.
City of San José open data — "Park." Parks and trails across San José, Santa Clara County and parts of San Mateo County, including land managed by Midpen, the County and the State. Available as GeoJSON. Licensed Creative Commons Attribution — attribution is required. Includes open, closed, future, seasonal and under-construction sites.
City of San José open data — "Park Amenities and Sports Fields." Amenities per city park, including playgrounds by age type, sports fields and courts.
Santa Clara County Parks GIS Hub (gisdata-sccparks.hub.arcgis.com). Trails, points of interest and park boundaries, with trail attributes such as width, recreation type and whether dogs are allowed. Record the license terms before ingesting. The County states its GIS data is provided as is and that official sources should be consulted for verification — the trail disclaimer in C3 reflects this. Note this is a different host from sccgov.org, which refused automated requests.
Join parks to Verdure's existing places by geometry, not name, so a park and its events connect.
C2 — Park guide (free)
A park detail page combining what no other app puts together:
Amenities: playgrounds with their age range, restrooms, drinking water, picnic areas, sports fields and courts, dog areas — shown only where the data confirms them
"Good for ages X–Y" derived from playground age-type data
Trails in this park (C3)
Events happening at this park this week — the combination that makes this Verdure's, not a directory
Hours, accessibility and entrance details where the data provides them
The organizer's place story from F1, where one exists
Status respected: a closed, future or under-construction site is never shown as open
Filters in Discover and Map: playground for toddlers, dog-friendly, restrooms, water
Attribution on every park page — for example, "Park data: City of San José, CC BY" — as each license requires
C3 — Trail overview (free)
Trails listed per park: name, length, type, width, dogs allowed and elevation where the data provides them
Trail lines drawn on the map as Verdure's own overlays, with the user's location
No turn-by-turn navigation, route-following or voice guidance. Wrong guidance in an open space preserve is a safety risk, the source data carries no accuracy guarantee, and dedicated navigation apps already serve this.
A visible notice on every trail view: "Trail information comes from official sources and may be out of date. Follow posted signs and check the park's official site for closures." with a link to that site
C4 — Offline packs (Verdure+)
A member downloads a park, a set of parks, or an area for the next seven days:
The park guide and amenities
Trail lines and park boundaries, drawn from stored data
Events at those parks and in the area, with details and compressed thumbnails
Places, the member's saved events and plans, and partner perks (view only)
Offline, the trail view still works. Trail lines and boundaries render from stored data, and the location dot works without cellular service because GPS does not need it.
Background map imagery is not included. MapKit provides no way to download its base map, and Apple's map imagery must not be cached. Offline, draw Verdure's overlays over whatever the system has cached, and say so plainly. A fully offline base map would need a different map engine and is out of scope.
Rules:
Entitlement checked server-side when a pack is generated; free accounts are refused by the server, not only the interface
Download size shown before downloading, with a hard cap — target 50 MB
Storage screen: packs, size, age, delete
Freshness: "downloaded X ago"; refresh on Wi-Fi when the app opens; packs expire after seven days
Online-only actions — RSVP, perk redemption, plan generation — say "available when you're back online"
No offline check-ins. Points are server-authoritative; a queued check-in replayed later would be a fraud path
C5 — Copy
Add "Offline park and place packs" to PaywallView.features, LISTING.md and the website pricing source in the same change that ships it — never before. Never describe it as "offline maps", because the base map is not included.
Done when: park and trail data ingest weekly with failures visible in the console; park pages show amenities, age suitability, trails and this week's events, with attribution and correct status; trail overviews show the safety notice and include no navigation; a member can download a park, use trail lines and location with no signal, see freshness and delete the pack; free accounts are refused server-side; offline check-in is impossible; copy says "offline park and place packs" and ships with the feature.

H. Production readiness checks
Two items that cannot wait for deployment, because the problems they prevent are invisible until then.
H1 — Composite indexes (not cuttable)
The live project has zero composite indexes. The Firestore emulator does not enforce composite indexes — it executes any valid query — so a query missing its index passes every local test and fails only in production. On the live project, that would break the feed, the planner or the console the first time it is used.
List every compound query in the app, functions and staff console: multiple equality filters, range filters combined with ordering, and array-contains with other filters
For each, confirm a matching entry exists in firestore.indexes.json; add any that are missing
Commit docs/FIRESTORE-INDEXES.md mapping every query to its index, with the file and line of the query
Add a script that fails if a compound query is added without a corresponding documented index
H2 — Crash reporting
When real people use Verdure, crashes must be visible. Integrate Firebase Crashlytics — free, and it needs no paid membership — with symbol upload configured so reports are readable.
Update the privacy policy and App Privacy answers in the same change. Crash data is collected data, and the existing statement that Verdure uses no analytics SDKs must stay true or be corrected.
Done when: every compound query is mapped to an index in docs/FIRESTORE-INDEXES.md, missing indexes are added, and a check fails on undocumented compound queries; Crashlytics reports a test crash with readable symbols from a physical device; privacy copy updated in the same change.

Ground rules
No paid membership is assumed. Anything requiring it is out of scope and recorded as untested.
Nothing is deployed. No billing change, deploy, environment flip or key rotation.
Do not modify ranking. Weights, signals and the synonym map are under evaluation.
Server-side authorization, always. The console interface is a convenience; the server is the gate.
No business's name on an offer it did not agree to. The agreement-on-file requirement is the rule, including in testing.
Honest copy, in both directions. Offline packs, park data, AR and live location alerts each change what Verdure offers or collects. Update the paywall, listing, website, privacy policy and App Privacy answers in the same change — never before the feature works, never after it ships.
Untested is not passed. Push delivery, real purchases, universal links and cellular behaviour stay untested until the membership and deployment exist.
Credit open data as its license requires. City of San José data is CC BY; attribution is not optional. Check and record every dataset's license before ingesting it.
A scraper must fail loudly — and its failures must now be visible in the console.
The emulator is not production. It ignores composite indexes and accepts any valid query. A passing local test is not proof a query will run live.
Build before you test. Any green result not produced by a fresh build is suspect.
Document with evidence. Every status claim needs a re-runnable command behind it.
